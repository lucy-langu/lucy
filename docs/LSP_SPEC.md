# Lucy Language Server Protocol — Editor Integration Specification

**Status:** protocol design; no production LSP server is shipped in this source archive.

## 1. Design constraint

The LSP must reuse Lucy's canonical lexer, parser, AST, symbol resolution, and diagnostic logic. It must not implement a second grammar in the editor adapter. The initial server should be read-only and analysis-focused; it must not execute the active document merely to provide completion or diagnostics.

## 2. Transport and lifecycle

- JSON-RPC 2.0 over standard input/output.
- One JSON message per `Content-Length` framed packet.
- All protocol logs go to stderr; stdout is reserved exclusively for protocol frames.
- Support `initialize`, `initialized`, `shutdown`, and `exit`.
- Handle `textDocument/didOpen`, `didChange`, `didClose`, and configuration changes.
- Advertise only capabilities actually implemented by the server.

## 3. Initial capability tiers

| Capability | Initial target | Notes |
|---|---|---|
| `textDocument/publishDiagnostics` | P0 | Lexer/parser errors and safe static diagnostics |
| `textDocument/completion` | P0 | Scope-aware names, builtins, modules, members |
| `textDocument/hover` | P1 | Function signatures, docs, inferred/declared type where known |
| `textDocument/definition` | P1 | Local symbols and imported source definitions |
| `textDocument/references` | P2 | Workspace symbol references |
| `textDocument/documentSymbol` | P1 | Classes, functions, variables, imports |
| `textDocument/signatureHelp` | P2 | Parameter labels and active argument |
| `textDocument/rename` | P2 | Only when symbol identity is reliable |
| `textDocument/formatting` | Deferred | Requires a separately specified formatter |
| `textDocument/semanticTokens` | Deferred | Do not advertise until stable token mapping exists |

P0 means required for the first usable server, not that it is already available.

## 4. Diagnostics

LSP diagnostics should map Lucy source spans to zero-based LSP line/character positions. The compiler/runtime's internal source positions should use one documented encoding convention and convert at the protocol boundary. Because UTF-8 byte offsets differ from UTF-16 code units, conversion must be tested with non-ASCII text before claiming editor correctness.

Each diagnostic should include:

- stable diagnostic code;
- severity;
- source (`lucy`);
- range and message;
- optional related information for import/dependency locations;
- optional quick-fix data only when the fix is semantics-preserving.

Runtime diagnostics that require execution must not be generated by running arbitrary project code in the language server.

## 5. Incremental document model

Maintain an in-memory document snapshot per URI. Apply incremental edits in protocol order and reject malformed ranges safely. Version numbers must prevent stale analysis results from overwriting newer diagnostics. Cancellation must be honored for superseded expensive analysis.

## 6. Completion

Completion should be derived from the current lexical scope and AST context, not a hard-coded list alone. Sources may include:

- visible local variables and parameters;
- functions and classes;
- builtins and built-in type methods;
- standard-library modules and exported members;
- project-local packages;
- imported symbols.

Do not trigger remote registry requests on every keystroke. Registry-backed completion, if later introduced, must be cached, cancellable, and explicitly configurable.

## 7. Workspace and security

- Treat workspace files as untrusted input.
- Do not execute build scripts or package code automatically.
- Restrict file access to workspace roots and configured Lucy library paths.
- Do not read environment secrets into completion or diagnostics.
- Avoid network access by default.
- Bound document size, recursion depth, and analysis time.

## 8. Editor configuration

A future server command should be stable and documented, for example `lucy lsp --stdio`. This command is proposed only. Existing `editors/` syntax/highlighting assets are not an LSP implementation.

## 9. Acceptance criteria

- Protocol conformance tests for initialize/shutdown and framing.
- Correct incremental change handling and cancellation.
- UTF-8 source to UTF-16 LSP range conversion tests.
- Stable diagnostics for malformed and valid files.
- Completion parity with REPL/runtime-visible symbols where applicable.
- No stdout contamination from logs.
- No document execution and no implicit network requests.
- Smoke tests in at least VS Code and one additional LSP client.
